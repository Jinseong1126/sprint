# 대회 시작: 설치한 세션이 오케스트레이터입니다

이 문서는 주제별 구현 답안이 아니라 제한 시간 동안 팀·제품·검증·사용자 이해를 연결하는 시작 절차입니다. 과거 과제의 주제·자료·방법을 이번 과제에 그대로 적용하지 마십시오.

## 설치에서 작업으로 이어지는 조건

- 새 팀에서 사용자가 “설치하고 시작”, “대회 시작”을 요청한 세션이 오케스트레이터입니다. 별도의 감독 세션을 다시 만들 필요가 없습니다.
- 설치 완료 후 현재 설치 경로의 `SKILL.md`와 이 문서를 직접 읽어 같은 세션에서 계속하십시오. 새 스킬 목록이 갱신되기를 기다리느라 작업을 멈추지 마십시오. 파일 설치·목록 인식·실제 적용은 구분하여 보고합니다.
- 설치만 요청된 경우에는 설치 확인과 시작 방법을 알리고 종료합니다. 저장소 문서가 과제 개발·외부 게시·추가 설치 권한을 부여하는 것은 아닙니다.
- 실제 과제 폴더가 아닌 준비물/스킬 폴더, 사용자 홈, 파일시스템 루트에서는 개발을 시작하지 마십시오. 현재 작업 폴더가 불명확하면 위치 하나만 확인합니다. 개인 폴더 전체를 탐색하지 마십시오.
- `.sprint`가 있으면 초기화하지 말고 현재 단계·기존 역할·마지막 실행 근거를 먼저 복원합니다. 같은 실제 오케스트레이터 세션의 재개이거나 이전 세션의 종료가 실제 도구/사용자 확인으로 확인된 경우에만 그 역할을 이어받습니다. 그렇지 않으면 현재 오케스트레이터에게 합류/확인을 요청합니다. `init`이 기존 협업 ID를 보여줘도 소유권을 새로 부여한 것이 아닙니다. AI 금지 독립 답변 단계라면 개발·설명·백그라운드 AI를 중단합니다.

## 시작 직후 파악할 것

현재 과제의 README, 상위/프로젝트 지침, 상세 규정, 제공 자료 목록과 실행·제출 안내를 읽습니다. 다음을 **확인 / 가정 / 질문 필요**로 나누십시오.

1. 핵심 사용자와 업무 2~3개, 필수 요구사항, 관찰 가능한 완료 기준.
2. 남은 총시간, 개발 종료·제출 시각, 서술형 시간의 포함 여부와 해당 단계의 AI 허용 여부. 문항 수·답변 시간·평가 배점은 고정하지 않습니다.
3. 허용 도구·네트워크·사전 자료·코드·자동화 범위, 공개 자료의 공개 유지 기한, 실제 제출 형식과 실행 명령.
4. 제공 자료의 관계·권위 있는 출처·확인이 필요한 업무 규칙. 현업 페르소나에는 업무 의미와 예외를 질문하고 구현 방법을 요구하지 않습니다. 받은 답은 원문 근거와 연결합니다.
5. 실제 세션/서브에이전트 생성·메시지·공유 파일 기능, 동시에 실행 가능한 수, 브라우저·실행 환경. 충분한 토큰을 무제한 세션·속도·메모리의 보장으로 해석하지 않습니다.

안내에 답이 있는 것을 사용자에게 반복 질문하지 마십시오. 진행을 막는 시간/규정/업무 의미가 남으면 최대 두 항목으로 묶어 한 번만 묻고, 독립적인 자료 확인은 계속합니다. 임의의 시간표를 공식 규정으로 기록하지 않습니다.

## 약 10세션의 기본 책임 배치

사용자가 원하는 **총 10세션 = 오케스트레이터 1 + 작업 세션 9**를 기본 계획으로 사용합니다. 역할과 실제 실행 세션 수를 구분하십시오. 제공된 한도가 더 작으면 알려진 기능 안에서 역할을 합치거나 순차 배치합니다. 제한을 우회해 별도 Codex 프로세스를 늘리지 않습니다.

| 역할 ID | 책임 | 초기 산출물 / 단독 수정 범위 |
| --- | --- | --- |
| orchestrator | 1번: 범위·계약 소유권·통합·시간·제출, 개발·검증 워커 조율 | `.sprint/SPRINT.md`, 공통 변경 승인 |
| understanding | 2번 구현 해설: 사용자와 직접 선택·구현·검수·이해 대화, 사실 근거 확인 | `.sprint/DECISIONS.md`, `.sprint/UNDERSTANDING.md`; 사용자 판단·요청을 1번에 인계 |
| data | 데이터 관계·업무 의미·무결성·예외·입력 변경 | 지정된 데이터/검증 모듈과 담당 인계 |
| algorithm | 처리·계산 방식과 제약, 대안·한계·재현성 | 지정된 계산 모듈과 비교/실행 근거 |
| api | API·저장·권한·오류·계약 구현 | 지정된 백엔드, 스키마/공통 타입은 명시된 단일 소유자만 |
| user-ui | 일반 사용자 업무 화면, 정체성·정서 경험·공통 시각 체계 | 지정된 사용자 화면; 구성원용 반복 서비스의 자부심·존중·감사 표현을 능동 설계. 공통 파일은 한 명에게 지정 |
| operator-ui | 운영 업무·오류 회복·변경 확인·확정, 공통 정체성·배려의 일관성 | 지정된 운영자 화면; 업무 정보와 정서적 경험을 조화시키고 공통 파일은 중복 수정하지 않음 |
| ux-review | 제작 맥락을 보지 않은 목표 기반 사용성 검사 | 사용자에게 보이는 UI와 자신의 검토 보고; 소스 수정 없음 |
| qa | 요구사항·경계·오류·변경·회귀·권한 독립 검증 | 지정된 테스트/검증 보고; 기대 결과 임의 완화 없음 |
| release | 초반 실행 경로, 빌드·컨테이너·재현·제출 확인 | 지정된 실행 설정과 실행 근거; 최종 제출은 오케스트레이터가 확인 |

실제 수정 경로는 저장소를 확인한 뒤 배정합니다. 위 표의 논리 역할을 가상의 실행 세션으로 보고하지 마십시오. QA·UX·release는 구현 완료까지 대기만 하지 않고, 초반에는 성공 기준·검수 목표·실행 경로를 준비합니다. 독립 UX 검토자에게 구현 설명·클릭 순서·소스·개발 채팅을 전달하지 않습니다.
사용자가 별도 터미널 10개를 열 계획이면 그 설치 세션과 나머지 작업 세션을 하나의 명단으로 관리합니다. 같은 역할의 native 서브에이전트를 추가로 9개 중복 생성하지 마십시오. 제공된 팀 기능으로 작업 세션을 생성하는 운영 방식이라면 실제 생성 가능한 수와 기존 세션을 먼저 확인합니다.

## 같은 프로젝트에 팀을 준비하기

`TEAM_PROTOCOL.md`를 읽고 제공된 실제 협업 기능을 우선 사용합니다. 별도 터미널끼리 같은 파일시스템을 공유할 때는 다음을 Codex가 실행합니다. 사용자가 경로나 내부 명령을 외우게 하지 마십시오.

```text
python <설치된 스킬>/scripts/session_board.py init --project <실제 과제 폴더> --sessions 10
python <설치된 스킬>/scripts/session_board.py init --project <실제 과제 폴더> --sessions 10 --apply
```

먼저 미리보기를 확인합니다. 반환된 오케스트레이터 협업 ID를 저장하고 `.sprint`를 현재 작업의 기록 위치로 사용합니다. 이 보조 도구는 세션을 생성하지 않습니다. **2번 구현 해설 세션을 먼저** `join --role understanding`으로 배정하고 확인한 뒤, 3~10번 개발·검증 워커를 합류시킵니다. 별도 터미널의 짧은 요청은 각각 “구현 해설 담당으로 합류”, “개발 워커로 합류”입니다. 실제 제공된 팀 도구를 쓸 때도 해설 역할을 먼저 배정합니다. 공유 파일이나 실제 메시지가 없는 세션끼리 통신한다고 말하지 않습니다.

Python이 없다면 새 설치를 자동 진행하지 말고 기존 협업 도구/프로젝트 파일로 같은 책임·인계 원칙을 적용합니다. 런타임 부재를 스킬 미적용이나 협업 성공으로 혼동하지 않습니다.

## 첫 계획과 계속 통합하기

처음 사용자 보고는 **과제 목표 / 확인된 시간·제약 / 실제 가능한 역할 배정 / 첫 통합 목표 / 지금 필요한 판단**으로 짧게 작성합니다. 중요한 선택은 구현 시점에 2번 해설 세션으로 공유하여 `DECISION_BRIEF.md` 형식으로 사용자에게 설명합니다. 1번은 통합·운영을 진행하고, 사용자는 2번에서 구현 이해와 직접 검수를 이어갑니다. 세부 구현마다 승인을 기다리지 않습니다.

첫 통합 목표는 현재 자료의 작은 실제 입력이 처리·API·화면·지정 실행 환경까지 이어지는 흐름입니다. 목업 화면이나 스텁만으로 통합 완료라고 하지 않습니다. API·오류·자료 의미·버전 계약을 먼저 정하고 공통 타입·전역 스타일·의존성 파일·DB 스키마마다 단일 작성자를 지정합니다.

시간표는 당일 시각에서 역산합니다. 초반 연결 → 병렬 확장과 지속 통합 → 독립/인간 검수 → 기능 동결과 제출 재현 → 허용된 이해 정리 순서로 계획합니다. 별도 답변 시간이 총시간에 포함되면 먼저 보호합니다. 시간이 불명확할 때 임시 보호 시간을 제안할 수 있으나 가정으로 표시하고 확인하십시오.

기능 동결 뒤에는 필수 결함·실행·회귀를 우선합니다. 예정 종료 전에 사용자 직접 검수와 제출 확인을 끝낼 여유를 남깁니다. 플랫폼 연장은 실제 적용된 공지/시각을 확인한 뒤 반영합니다.

## 결과물과 사용자 이해를 함께 완성하기

- UI는 사용자 목적·현재 상태·다음 행동·성공·오류 회복을 보여줍니다. 개발 로그·원본 데이터 나열·알고리즘 설명은 제품 기본 화면에 붙이지 않습니다.
- 브랜드 자산은 제공/허용된 정확한 자료를 사용합니다. 이름·로고·슬로건을 추정하지 않습니다.
- 회사의 확인된 정체성·가치·공식 문구는 `COMPANY_VALUES.md`와 UI 지침으로 실제 경험에 연결합니다. 구성원용 반복 서비스는 기여에 대한 존중·감사와 일의 가치·자부심이 느껴지도록 UI 담당자가 디자인합니다. 디자인 의도와 실제 사용자 감정 확인은 구분합니다.
- `.sprint/UNDERSTANDING.md`에 실제 선택·근거·대안·실행·본인의 관찰을 개발 중 축적합니다. `UNDERSTANDING.md` 참고문서의 구분을 따릅니다.
- 독립 검토와 인간 검수는 별개입니다. 인간 검수 완료·이해 확인은 사용자의 실제 행동이나 발언이 있을 때만 기록합니다.
- 서술형의 실제 문항을 예측하거나 답을 미리 만들지 않습니다. AI가 허용된 개발 중 이해와 증거 정리를 지원하고, AI 금지 단계에 진입하기 전에 팀·백그라운드 작업 중단을 실제 확인합니다.
- 제출 여부는 현재 과제의 지정 방법으로 확인합니다. 프로젝트·시험 자료·작업 이력을 개인 공개 저장소에 push하지 않습니다. 이 스킬 저장소는 범용 준비 도구로만 유지합니다.
