# 같은 프로젝트의 여러 세션 운영

## 실제 기능과 기록을 구분하십시오

native 팀/서브에이전트·메시지 기능이 제공되면 그 실제 API와 제한을 사용합니다. 역할 카드에는 목표·입출력 계약·허용 파일·금지 범위·완료 기준·검증·인계를 적습니다. 독립 검토자는 새 컨텍스트를 사용하고, 구현 대화가 넘어갔다면 독립성의 한계를 밝힙니다.

별도 터미널은 자동으로 대화를 공유하지 않습니다. 같은 프로젝트 디렉터리를 공유하는지 확인합니다. `session_board.py`는 **역할 등록과 인계 파일만** 관리하며 에이전트 생성·메시지 전달·프로세스 감시·권한 통제 엔진이 아닙니다. 등록을 실제 실행이나 완료의 증거로 사용하지 않습니다.
같은 사용자 홈·실행 환경을 공유하면 한 번 설치한 스킬을 여러 세션에서 사용할 수 있습니다. 별도 컨테이너/사용자 홈은 별도 설치가 필요할 수 있습니다. 작업자에게 `.sprint`가 보이지 않으면 새 팀을 만들지 말고 실제 공유 경로/협업 도구를 확인합니다.

## 설치 세션과 합류 세션

- “설치하고 시작”을 요청한 새 팀의 세션: `COMPETITION_START.md`에 따라 오케스트레이터로 초기화합니다. 기존 `.sprint`가 있으면 덮어쓰지 않고 먼저 읽습니다. 같은 실제 세션의 재개 또는 이전 오케스트레이터 종료가 확인된 경우에만 오케스트레이터 역할을 이어받습니다. `init`의 existing 결과나 그 안의 협업 ID는 신규 소유권 부여가 아닙니다. 다른 활성 오케스트레이터가 있으면 그 팀에 합류/확인을 요청합니다.
- 다른 세션에서 “스프린트 합류”: 먼저 현재 프로젝트의 `.sprint` 단계와 안내를 읽고, helper의 `join`으로 비어 있는 역할을 원자적으로 받습니다. 실제 오케스트레이터의 역할 지정이 있으면 `--role`로 요청합니다.
- 수동 터미널과 native 작업자는 하나의 명단으로 관리합니다. 사용자가 직접 연 작업 세션을 대신할 native 세션을 중복 생성하지 않습니다. 실제 native 세션 ID와 helper의 협업 ID가 다르면 오케스트레이터가 그 대응을 기록합니다.
- 역할 수가 실제 허용 세션 수보다 많으면 오케스트레이터가 소유권을 분명히 하여 겸임합니다. 수를 맞추려고 불필요한 작업·중복 구현을 만들지 않습니다.
- 역할을 받은 것만으로 소스 수정 범위가 정해지지 않습니다. 계약과 파일 소유권이 정해질 때까지 자료 분석·테스트 목표 준비 등 독립적인 일만 합니다.

Codex가 사용하는 명령 예시입니다. `<스킬>`과 `<과제>`는 현재 환경에서 확인한 경로이며 사용자가 외우는 명령이 아닙니다.

```text
python <스킬>/scripts/session_board.py join --project <과제>
python <스킬>/scripts/session_board.py join --project <과제> --role qa --session <협업ID>
python <스킬>/scripts/session_board.py status --project <과제>
python <스킬>/scripts/session_board.py handoff --project <과제> --role <역할> --session <협업ID> --state review --summary <실제결과> --evidence <명령·출력·버전근거> --next <다음담당에게필요한것>
```

협업 ID는 helper가 반환한 논리적 소유 표식입니다. native 세션 인증정보나 프로세스 생존 증명이 아닙니다. 한 역할에 두 개의 살아 있는 작성자가 같은 ID로 일하게 해서는 안 됩니다.

## 공유 파일의 작성자

- `.sprint/SPRINT.md`: 오케스트레이터만 통합 상태·소유권·마지막 검증 버전을 갱신합니다.
- `.sprint/CONTRACTS.md`: 오케스트레이터가 지정한 계약 소유자만 갱신합니다. 다른 역할은 변경 제안을 인계하고 임의로 계약을 바꾸지 않습니다.
- `.sprint/DECISIONS.md`, `.sprint/UNDERSTANDING.md`: understanding 담당 한 명이 실제 코드·실행 근거와 사용자 발언을 확인하여 기록합니다. 이 역할이 없으면 오케스트레이터가 소유합니다.
- `.sprint/handoffs/<역할>.json`: 각 역할이 자기 파일만 작성합니다. 근거가 없으면 `done`이라고 쓰지 않습니다.
- 실제 앱 파일: 역할 카드의 허용 경로만 수정합니다. 공통 컴포넌트·스타일·스키마·의존성 파일에는 단일 작성자가 있습니다.

`SPRINT.md`는 마지막 통합 요약이며 실시간 장부가 아닙니다. 현재 등록·역할 인계는 helper의 `status`와 claim/handoff 파일로 확인하고, 불일치하면 오케스트레이터가 요약의 기준 시각·버전을 갱신합니다. 작업자는 오래된 요약을 고치려고 공유 파일 소유권을 넘지 않습니다. 실제 메시지 도구가 없으면 작업 시작·인계 확인·통합·단계 전환 같은 체크포인트에서 인계를 확인하며, 파일에 쓴 것을 상대가 이미 읽었다고 가정하지 않습니다.

상태는 `working / blocked / review / done / stopped`로 인계합니다. 계약을 기다리는 상태는 blocked와 필요한 입력을 적고, 임의의 API·가짜 완료로 우회하지 않습니다. 간단한 국소 구현에 매번 사용자 승인을 요구하지 않습니다.

완료 인계에는 **변경한 경로 / 충족 요구사항 / 실행 명령과 exit code / 관찰 결과와 버전 / 남은 한계 / 다음 담당자 입력**이 포함되어야 합니다. 전체 테스트 통과만으로 실제 업무·UI·제출 요구사항 전체를 만족했다고 하지 않습니다.

## 중단·재접속

재접속 시 현재 단계, 역할 기록, 작업 파일, 실행 중인 서버/작업, 마지막 통합 근거부터 확인합니다. 서버·마이그레이션·생성을 중복 실행하지 않습니다. 같은 세션 또는 중단이 실제 확인된 역할을 재개할 때만 기록된 협업 ID로 `join --session <기존ID>`를 사용합니다.

새 세션으로 바꾸는 경우 오케스트레이터가 이전 실제 세션의 종료를 제공된 도구나 사용자 확인으로 먼저 확인합니다. 경과 시간만 보고 죽었다고 가정하거나 claim을 지우지 않습니다. 자동 역할 탈취·자동 stale lock 해제·자동 재배정은 제공하지 않습니다. 부분 claim/불완전 초기화가 있으면 상태를 보존하고 오케스트레이터가 검사합니다.

## 단계 전환과 AI 중단

단계는 `planning → development → freeze → independent → submitted`입니다. `independent`는 **당일 규정상 AI를 쓰면 안 되는 답변 단계**를 의미합니다. AI가 허용된 정리 단계와 혼동하지 마십시오.

```text
python <스킬>/scripts/session_board.py phase --project <과제> --session <오케스트레이터ID> --value development
python <스킬>/scripts/session_board.py phase --project <과제> --session <오케스트레이터ID> --value freeze
```

AI 금지 시각이 오기 전에 실제 생성/메시지 도구로 모든 작업자에게 중단을 전달하고 종료·중단 ACK를 확인합니다. 수동 터미널을 제어할 수 없으면 사용자가 실제로 종료/중단하도록 알립니다. 각 역할의 `done/stopped` 인계와 실제 실행 상태를 확인한 뒤 오케스트레이터가 independent로 바꿉니다.

helper는 claimed 작업자 모두의 명시적인 `done/stopped` 인계 없이는 independent 전환을 거부하고, 해당 단계의 새 join/handoff를 막습니다. **파일의 단계 변경만으로 실행 중인 AI가 물리적으로 멈추지는 않습니다.** 오케스트레이터도 이 단계에서 모델 응답·추가 도구 작업·답변 생성을 멈춥니다. 단계는 임의로 되돌리지 않습니다.

**실제 규정과 AI 금지 시각이 장부 상태보다 우선합니다.** ACK가 없거나 helper 전환이 실패해도 확인/복구를 계속하느라 AI 금지 시간을 넘기지 마십시오. 허용 시간 안에 미확인 중단 상태를 남기고 사용자에게 실제 터미널 중단이 필요한 부분을 알린 뒤, 금지 경계에서는 오케스트레이터 자신도 중단합니다. 장부가 planning/freeze로 남았다는 이유로 AI 사용이 허용되는 것은 아닙니다.
