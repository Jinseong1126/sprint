# 독립 업무 수행 검수

## 어떤 검증인가
기능 검증: 정해진 절차와 입력으로 정답 동작을 확인합니다.
사용성 검증: 목표만 주어지고 경로는 모르는 상태에서 수행합니다.
둘을 따로 보고하십시오. AI 사용성 검사는 인간 검사를 대체하지 않습니다.

## 검토자에게 제공할 것
허용된 앱 주소, 테스트 사용자 역할·계정, 실제 업무 목표, 알려진 규정·접근 제한만 전달하십시오.
정답 클릭 순서·구현 파일·API 이름·개발자의 장문 설명은 주지 마십시오.
가능하면 새 컨텍스트/독립 서브에이전트를 사용하고 실제로 분리되지 않았다면 한계를 보고하십시오.
검토자는 소스·DB·API로 정답을 찾아가거나 숨은 상태를 읽지 말고 브라우저가 노출하는 UI만 사용하십시오.
테스트 자체가 데이터 수정/게시를 일으키면 허용된 테스트 자료에서만 실행하십시오.

## 도구와 관찰 수준
1. 먼저 제공된 로컬 브라우저 도구가 실제로 열리는지 확인하십시오.
2. 접근성 트리/DOM으로 의미와 조작을 확인할 수 있지만, 픽셀 배치와 시각적 우선순위까지 봤다고 말하지 마십시오.
3. 시각 캡처는 명시적으로 허용된 경우에만 사용하십시오. 기본적으로 화면 캡처·영상·trace·인증상태 저장은 하지 마십시오.
4. 도구가 없거나 금지된 경우 코드 검토를 브라우저 검수로 바꾸어 부르지 말고 사용자 직접 검사로 인계하십시오.
5. 기존 agent-browser/Playwright/MCP 중 허용되고 동작하는 것 하나를 우선하십시오. 신규 브라우저·확장·외부 서비스는 자동 설치하지 마십시오.

## 검사 방법
사용자 목표를 하나 받아 보이는 이름과 피드백을 따라 실행하십시오.
헤맸음·잘못 선택함·이유를 추측함·완료인지 모름·복구 불가를 실패 신호로 기록하십시오.
기능이 DOM에 있어도 숨김·읽기 어려움·오류 문구 불일치로 발견하기 어렵다면 구분하여 보고하십시오.
비슷한 길을 두 번 실패하면 무한 탐색하지 말고 해당 문제를 제출하십시오.

## 보고 형식
목표 / 관찰 수준(DOM 또는 시각 또는 인간) / 재현 단계 / 막힌 지점 / 기대 행동 / 실제 관찰 / 심각도 / 재검증.
코드는 수정하지 말고 통합 책임자에게 전달하십시오. 수정 담당자는 동작 가능한 해법을 제시하고 같은 목표로 재검증하십시오.
자동 점수나 모델의 자신감을 합격 기준으로 쓰지 마십시오.

## 인간 확인
핵심 업무 1~2개는 사용자에게 조작법 없이 목표만 주어 직접 해보게 하십시오.
다른 검증에서는 구체적인 재현 입력을 안내할 수 있습니다. 두 방식을 혼동하지 마십시오.
관찰한 결과를 사용자가 말하기 전까지 사용자 검수 완료로 기록하지 마십시오.
