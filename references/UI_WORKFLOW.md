# 업무가 보이는 UI

## 디자인 원칙
'단순함'은 기능 삭제나 모든 정보를 숨기는 것이 아니라, 사용자가 지금 해야 할 일을 분명하게 하는 것입니다.
기업 제품다운 완성도는 정확한 브랜드 자산, 일관된 용어, 안정적 상태 표시, 업무 흐름에서 드러납니다.
목표는 처음 들어온 사용자도 핵심 업무를 쉽게 끝내고 매일 쓰고 싶은 일관된 제품 경험입니다. 로고·이미지·문구·여백까지 정확한 정체성과 맥락에 맞게 다듬습니다. 시각적·사용성 완성도는 초기 화면 계약과 구현부터 반영하며, 기능 구현 후의 마지막 장식 단계로 미루지 않습니다.
제공·사용 허가된 자산만 쓰고 슬로건·로고를 지어내지 마십시오. 기존 디자인 시스템이 있으면 우선하십시오.
회사 가치와 행동 원칙은 `COMPANY_VALUES.md`에 따라 확인하고, 사용자에게 줄 경험·실제 동작·표현·완료 기준에 연결합니다. 브랜드 자산의 정확성뿐 아니라 제품을 쓰는 과정에서 그 조직의 가치와 신뢰·자부심이 느껴져야 합니다. 가치 문구나 배지를 많이 붙이는 것을 반영 완료로 취급하지 않습니다.
홍보용 첫 화면과 로그인 후 업무 화면을 구분하십시오. 사진·감성 문구로 업무 버튼과 상태를 밀어내지 마십시오.

## 구현 전 화면 계약 (각 핵심 화면 6줄 이내)
대상 사용자 / 현재 목표 / 반드시 알아야 하는 정보 / 중심 행동 / 성공 신호 / 실패·복구 경로.
어떤 데이터가 있다는 이유만으로 박스·지표·표를 만들지 마십시오.
요구사항마다 카드 하나씩 만드는 대신 사용자가 수행하는 순서로 구성하십시오.
공통 색·간격·타이포·상태 표현과 용어를 정하고 양쪽 UI 담당자가 공유하십시오.

## 상태에 따라 보여줄 것
필요한 상태만 구현하되 다음을 검토하십시오:
첫 사용·미선택 / 로딩 / 입력 오류 / 진행 차단 / 준비 완료 / 처리 중 / 성공 / 조건 변경으로 결과가 오래됨 / 권한 없음.
각 상태는 '현재 무엇인가, 지금 할 수 있는 것은 무엇인가, 다음 결과가 무엇인가'에 답해야 합니다.
동시에 동일한 강조 버튼을 여러 개 경쟁시키지 마십시오. 오류가 있는데 단순 '완료' 배지를 보이지 마십시오.
진행률·실시간 위치·최적성은 실제 측정에 기반하지 않으면 그렇게 표현하지 마십시오.
원본 JSON·디버그 로그·개발 코멘트·불필요한 총건수는 기본 업무 화면에서 분리하십시오.
구현 이유·대안·개발 검증 설명은 2번 구현 해설 세션과 개발 기록에서 다룹니다. 제품 화면에는 사용자가 지금 판단하고 행동하는 데 필요한 정보와 오류 회복 경로를 둡니다.
필요한 감사 기록과 상세 오류는 명확한 진입점으로 접근 가능하게 두십시오.

## 오류와 입력
버튼은 결과를 설명하는 동사+대상으로, 필드는 영구 라벨로 표시하십시오.
오류는 무엇이/어디서 잘못됐으며 어떻게 고치는지, 가능하면 해당 행·필드와 연결하십시오.
경고와 배차/저장 등을 차단하는 오류를 구분하고 유효한 이전 결과를 조용히 덮어쓰지 마십시오.
파괴적 작업은 안전한 회복 또는 명확한 확인을 제공하십시오. 인증·권한은 UI 숨김만으로 구현하지 마십시오.

## 선택적 외부 참고
화면을 덜어낼 때 upstream/distill.md, 문구·오류를 다듬을 때 upstream/clarify.md를 읽으십시오.
이 두 파일은 Impeccable 원문 참고자료입니다. 제품 필수 기능·접근성·업무 판단 정보를 삭제하라는 허가가 아닙니다.
원문의 템플릿 `{{...}}`와 후속 polish 호출은 이 묶음에서 실행하지 마십시오.
전체 Impeccable/CLI/훅은 설치되어 있다고 가정하지 마십시오.

## 제작자 자체 검수와 별도 검수
제작자는 기능·키보드·좁은 화면·긴 글자·오류·기본 접근성을 확인하십시오.
새 검토자는 BLIND_REVIEW.md에 따라 사용법을 듣지 않고 업무를 수행하십시오.
비평 결과는 취향보다 업무 차단→잘못된 판단→불필요한 탐색→미관 순으로 수정하십시오.
기능은 되지만 처음 온 사용자가 경로를 찾지 못하면 완료가 아니라 재작업 대상입니다.
