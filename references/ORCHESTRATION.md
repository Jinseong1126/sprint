# 분업과 통합

## 역할은 책임이고 세션 수는 수단입니다
기본 동시 작업 목표는 6개 이하입니다. 이는 실험 시작값이며 최대 성능의 보장이 아닙니다.
독립 작업·리소스·제공 도구가 확인되면 추가하고, 통합 대기/타임아웃/중복 변경이 늘면 줄이십시오.
충분한 토큰 안내를 무제한 동시 실행 허가나 자원 보장으로 해석하지 마십시오.
실제 제공된 native subagent/팀 기능을 사용하십시오. 모르는 CLI 명령이나 모델 이름을 생성하지 마십시오.
없는 기능은 단일 에이전트의 순차 역할로 대체하고 한계를 알리십시오. 모델·버전·권한은 변경하지 마십시오.

## 책임 배치
- 통합 책임자: 스코프, 공통 계약, 우선순위, 파일 소유권, 전체 실행. 사용자에게 보고하는 단일 창구.
- 제품/이해 담당: 업무 의미, 짧은 선택 설명, 요구사항-검증 연결, 사용자 직접 검수. 코드·기록으로 사실 확인.
- 데이터/업무 담당: 입력 정규화, 출처 우선순위, 예외, 오류 차단. 중요 의미를 임의 결정하지 않음.
- 계산/백엔드 담당: 알고리즘·API·저장·권한. 복잡하면 분리하되 계약을 먼저 확정.
- 사용자 UI / 운영자 UI 담당: 상태와 업무 흐름 단위 구현. 공통 스타일·타입의 소유자는 한 명.
- 독립 QA/사용성 담당: 제작 맥락 없이 실제 목표 수행, 데이터 변경/회귀. 코드 작성자와 분리.
- 실행/릴리스 담당: 초반부터 빌드·컨테이너·제출 실행. 후반에 처음 시작하지 않음.
위 역할을 모두 처음부터 별도 세션으로 띄울 필요는 없습니다. 인접 책임을 병합하고 단계에 따라 재배치하십시오.

## 나누기 전에 정할 것
1. 핵심 업무와 실제 완료 조건.
2. 입력/출력 데이터 타입, 날짜·시간 의미, API 오류 형식, 권한. 확인된 규칙/가정을 구분.
3. 공유 컴포넌트, 의존성 파일, DB 스키마, 전역 CSS에는 단일 작성 책임.
4. 첫 통합본의 범위. 미완성 화면·목업 데이터·API 스텁은 실제 완료로 간주하지 않음.

## 작업 인계 형식
각 작업은 '목표 / 입력·계약 / 수정 가능 경로 / 금지 경로 / 완료 기준 / 실행할 검증 / 넘길 결과'로 지정하십시오.
서로 다른 파일을 편집해도 계약이 바뀌면 상대방에게 알리십시오. 계약 소유자 승인 없이 임의 변경하지 마십시오.
허용되고 숙련된 경우에만 worktree를 쓰십시오. 이를 권한·정책 우회나 시험 자료 외부 반출에 쓰지 마십시오.
충돌을 피하려고 같은 lockfile·전역 스타일·문서에 모든 에이전트를 쓰기 권한으로 몰지 마십시오.

## 최소 상태 기록
현재 과제의 허용된 위치에 `SPRINT.md` 하나로 범위·담당·요구사항별 상태·마지막 통합 검증을 관리하십시오.
중요 결정만 `DECISIONS.md`에 기록하고, 병렬 작업이 있을 때만 역할별 handoff 파일을 추가하십시오.
통합 상태는 통합 책임자만 갱신하고 각 담당은 자기 인계 파일만 갱신하십시오.
사용자 승인 원문 또는 관찰 결과와 코드/명령/버전 근거를 연결하십시오. 과도한 보고서는 만들지 마십시오.

## 시간 보호
실제 규칙에 맞춰 총시간/답변시간/제출시간을 기록하십시오. 180분 전체 과제 예시:
0~15 방향·계약, 15~60 첫 작동 흐름, 60~100 사람/독립 검수와 보완,
100~125 새 기능 동결·결함/사용성, 125~140 최종 실행·이해, 마지막 40분 독립 답변.
이는 적응 가능한 기본안입니다. 60분 목표가 지연되면 부가 범위를 줄이고 사용자에게 선택지를 주십시오.
위험한 오류나 필수 조건을 숨기며 시간표만 맞추지 마십시오. UI 필수 요구사항은 부가 장식으로 축소하지 마십시오.

## 재접속과 변경
재시작 후 현재 파일·실행 중 프로세스·마지막 검증 버전을 먼저 확인하십시오.
이미 실행 중인 서버/마이그레이션/생성을 중복 실행하지 마십시오.
후반의 중요한 변경은 '이전 설명→바뀐 점→이유→재검증'으로 전달하십시오.
사용자의 답변 시점에 코드가 크게 바뀌지 않도록 마지막 후보를 안정화하십시오.
